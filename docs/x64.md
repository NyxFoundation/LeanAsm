# x86-64 foundation

LeanAsm supplies a scalar integer subset of x86-64 long mode alongside RV64IM.
It generates native code for Linux using the System V AMD64 integer calling
convention. It does not execute existing ELF binaries or translate RISC-V
programs automatically. No Ethereum-specific operations are in this backend.

## Generate and call a function

Requirements: the pinned Lean toolchain, GNU binutils with x86-64 and
`{disp32}` pseudo-prefix support, and GCC. Native execution requires Linux
x86-64.

From the repository root:

```sh
lake build
mkdir -p build
lake env lean --run Examples/X64.lean > build/x64.s
gcc -Wall -Wextra -Werror Examples/X64.c build/x64.s -o build/x64-example
./build/x64-example
```

The program prints `5050`. The Lean example uses physical registers, labels,
and flag-based branches. Its first argument is in RDI and its result in RAX.

For direct instruction programs:

```lean
import LeanAsm

open LeanAsm.X64

def addWords : Program :=
  [.mov .b64 .rax (.reg .rdi),
   .alu .add .b64 .rax (.reg .rsi),
   .ret]

#eval LeanAsm.emitAsm "add_words" addWords
#eval LeanAsm.lowerX64 addWords
#eval encodeProgram addWords
```

`lowerX64` returns `Except X64.Error X64.Program`. `emitAsm` retains its
shared `Except String String` interface. Direct programs validate operands
before either capability succeeds. Symbolic programs implement both capabilities,
but lowering requires closed, code-only input.

## Supported operand forms

| Family | Forms |
| --- | --- |
| MOV | Register from register/memory; memory from register; register immediate |
| LEA | 64-bit effective address into a register |
| MOVZX / MOVSX / MOVSXD | Widening byte/word sources; signed dword to qword |
| ADD / ADC / SUB / SBB / AND / OR / XOR / CMP / TEST | Register destination, register/memory source or immediate |
| NOT / NEG / INC / DEC | Register operand |
| SHL / SHR / SAR / ROL / ROR | Register operand, imm8 or CL count |
| MUL / one-operand IMUL / DIV / IDIV | Register/memory source and architectural accumulator pair |
| Two-operand IMUL | Word/dword/qword register destination, register/memory source |
| CWD / CDQ / CQO | Sign extension for implicit division operands |
| BSWAP | Dword/qword register |
| SETcc / CMOVcc | All 16 conditions; low-byte register / word-or-wider register destination |
| JMP / Jcc / CALL | Direct rel32; register-indirect JMP and CALL |
| PUSH / POP / RET | 64-bit register pushes/pops and near return |
| NOP / CLC / STC / CMC | No operands |

The general arithmetic and move widths are 8, 16, 32, and 64 bits.
There are no high-byte AH/BH/CH/DH operands. Byte and word writes preserve upper
register bits; dword writes clear the upper 32 bits. Immediate arithmetic on
64-bit operands sign-extends an imm32, whereas `movImm .b64` carries an imm64.
Unsupported width combinations are rejected, not expanded into macros.

Addresses support a base plus signed disp32, optional-base indexed SIB with
scales 1/2/4/8, and RIP-relative disp32. RSP cannot be an index; R12 can.
RIP-relative displacements are measured from the next instruction.
The omitted memory-destination arithmetic forms can be expressed with explicit
loads and stores; this is not an atomic substitute.

SIMD, floating point, AES/SHA extensions, atomics, privileged instructions,
syscalls, compatibility modes, a decoder, and an ELF loader are outside this
subset.

## Layout and execution

`encode` returns the bytes of one instruction. `Instr.byteSize`, symbolic
layout, instruction fetch, and RIP advancement all derive lengths from that
encoder. Direct branches always use rel32; MOV r64 immediate always uses imm64.
The emitter uses GNU `{disp32}` to prevent branch relaxation. It emits Intel
syntax and quotes validated symbol references so names such as `rax` remain
symbols, not register operands.

`X64.Symbolic.lower` checks duplicate/missing labels and rel32 ranges.
It resolves jumps, calls, and RIP-relative addresses within a code-only program.
Data sections, alignment directives, and external references are supported by
`Symbolic.emit`, not by the closed instruction-image model; lowering rejects
them rather than guessing their placement.

`execInstr` validates encoding before execution. `execSequence` folds a
supplied instruction list without following branches. To follow control flow,
construct an `Image` with `base` and `code`, then use `runUntil image stop fuel state`.
A typed image only fetches at its instruction boundaries; it does not decode
alternate instructions starting inside an encoding. CALL pushes the next RIP,
RET pops it, and division by zero or an overflowing quotient returns
`divisionError`.

Each arithmetic flag is `Option Bool`: `none` represents architectural
undefinedness. Reading an undefined flag returns `undefinedFlag`. Compound
conditions conservatively require all referenced flags to be defined.
Logical operations undefine AF, multiply defines only CF/OF, and division
undefines all arithmetic flags. Shift/rotate masking and undefined flag cases
are modeled separately. Initial registers and flags describe an explicit
machine state, not facts about a C caller; use `Flags.undefined` when incoming
flags are unknown.

Data memory consists of nonempty, disjoint, non-wrapping regions with write
permissions. Scalar accesses may be unaligned, but the full access must fit
inside one region. Images cannot overlap writable regions. This model does
not implement canonical-address faults, paging, segmentation, alignment-check
mode, concurrent memory ordering, or self-modifying code.

## System V AMD64 helpers

`LeanAsm.ABI.SysVAMD64` exports integer argument, return, caller-saved, and
callee-saved register lists. RSP preservation is handled by the stack helpers,
not included in the save lists. `enter locals` saves RBX, RBP, R12–R15 and
reserves enough space for locals, aligning RSP to 16 bytes before nested CALLs.
`leave locals` restores those registers and returns; use the same local size.
`functionBody` surrounds a fall-through body with that pair.

Entry RSP must be 8 mod 16, with a readable return address and sufficient
writable stack space. The helpers do not use the red zone or establish a frame
pointer. Oversized frames are rejected. Aggregate, floating-point, vector, and
variadic ABI classification and Windows calling conventions are not provided.

## Verification and trust boundary

```sh
lake env lean Tests/X64.lean
python3 Tests/X64/check.py
```

The Python test also builds the library and runs the Lean checks. It requires
Python 3, GNU `as`, `objcopy`, `nm`, `ld`, and GCC. It uses temporary
artifacts and standard-library Python only. It compares:

- Canonical encoding against independently assembled GNU instructions across
  registers, widths, immediate boundaries, REX/ModRM/SIB forms, and conditions.
- Register results and every architecturally defined arithmetic flag against
  native execution of both emitted assembly and directly encoded bytes.
- Closed symbolic layout against linked GNU bytes.
- C calls, saved registers, nested-call stack alignment, an unaligned byte-copy
  loop, and a two-limb carry-propagating addition routine.

These are executable checks, not proofs of ISA or hardware equivalence.
No correctness theorem is inherited from the existing RV64 proofs.
`LeanAsm.Rv64.SAsm`, `LeanAsm.Symbolic`, and `ABI.LP64` remain RISC-V-specific.
Consumers such as ssz-asm and p2p-asm still require separate routine, ABI,
and proof migrations.

Instruction behavior and encodings follow the
[Intel Software Developer's Manual](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html),
Volumes 1 and 2; ABI boundaries follow the
[System V AMD64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI).
